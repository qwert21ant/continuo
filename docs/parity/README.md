# Parity dumps

The files in this directory (`blocks-1.7.10.txt`, `blocks-1.21.11.txt`, `golden-1.7.10.txt`, `golden-1.21.11.txt`) are dumps of the fixture world described in `fixture-layout.md`, one canonical `index\tid\tstateKey\tdata` line per position. Hand-editing any of these files defeats their entire purpose, since `BlockParityTest` exists to prove what the two real adapters actually report, not what someone typed. But the two pairs are not the same kind of artefact, and must not be regenerated the same way:

- **`blocks-1.7.10.txt` and `blocks-1.21.11.txt` are dumps.** They are **generated by a human running the fixture in a real client of each version and pressing the dump keybind**, and are meant to be re-generated whenever the fixture, the client, or the adapter changes — that is what they are for.
- **`golden-1.7.10.txt` and `golden-1.21.11.txt` are frozen, human-reviewed copies, not dumps that happen to be re-run.** Each was taken once, by a human reading the corresponding `blocks-*.txt` file line by line and signing off that it is correct. Their entire value is *prospective*: they are what a **later** re-dump is measured against by `BlockParityTest.bothAdaptersMatchTheGolden`. **Never regenerate a golden from the same keypress that produced the current `blocks-*.txt`.** Doing so makes `golden == blocks` by construction, forever — the golden comparison degenerates into comparing a file to itself, and the one property a golden exists to catch (a change that breaks *both* versions identically, which the cross-version diff between `blocks-1.7.10.txt` and `blocks-1.21.11.txt` cannot see, since both sides would still agree with each other) silently disappears. Replacing a golden requires a fresh, line-by-line human review of the new dump against the old golden and the fixture layout — the same review that produced it the first time — not a keypress.
